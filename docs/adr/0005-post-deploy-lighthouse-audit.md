# Post-deploy Lighthouse audit, chained onto the existing deploy workflow

We audit the live production URL with Google's own `lighthouse` npm CLI/programmatic API (not `treosh/lighthouse-ci-action` or `@lhci/cli`, both of which bottom out in the same raw Lighthouse Result JSON for Core Web Vitals anyway, and neither of which is more actively maintained), run from a new `lighthouse` job appended to `.github/workflows/deploy.yml` with `needs: deploy` (not a separate `workflow_run`-triggered workflow file, which would add an extra event-propagation hop, a 3-level chain cap, and a first-run bootstrapping requirement that the triggering workflow already exist on `master`). The job commits its results back to `master` using the default `GITHUB_TOKEN`, which GitHub's own docs confirm does not re-trigger other `push`-triggered workflows — this is what actually rules out an infinite loop, not the choice of tool or trigger pattern. `lighthouse` requires Node 22, so the new job carries its own `actions/setup-node` step independent of `build`/`deploy`'s Node 20. This trades a small, self-contained addition to an existing, already-trusted workflow file for coupling the audit's own success/failure and runtime into that workflow's single run — acceptable here since a failed audit run only fails this one job, never the deploy that already succeeded before it starts. Full research backing this decision, with primary-source citations: [docs/research/lighthouse-widget.md](../research/lighthouse-widget.md). guntherjh/guntherjh.github.io#41.
