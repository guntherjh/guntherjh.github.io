# Coding Standards

Conventions this project follows in practice, written down so `/code-review` and future contributors have a documented baseline instead of "none found."

## Project structure (Eleventy)

- **Input directory**: `src/` — all templates, data, and static assets that get processed or copied live here.
- **Output directory**: `_site/` — generated by `npx eleventy`; never edit or commit its contents (gitignored).
- **Templating engine**: Nunjucks (`.njk`) for both HTML templates and Markdown processing (`markdownTemplateEngine`/`htmlTemplateEngine` are both set to `njk` in `eleventy.config.js`).
- **Layouts** live under `src/_includes/layouts/`. `base.njk` is the shared page shell (nav, footer, `<head>`); `post.njk` wraps it for individual blog posts.
- **Directory data files** (e.g. `src/posts/posts.json`) apply shared front matter — tags, layout, permalink template — to every file in that directory. Use this instead of repeating the same front matter block in every post.
- **Global data**: `src/_data/*.js` (e.g. `metadata.js`) for site-wide values — title, tagline, URLs, author info. Reference these via `{{ metadata.* }}` in templates rather than hardcoding them inline.
- **Passthrough copy**: static assets that need to reach the output unprocessed (CSS, `CNAME`) are registered explicitly in `eleventy.config.js` via `addPassthroughCopy` — don't rely on implicit copying.
- **ESM throughout**: `package.json` sets `"type": "module"`; config and data files use `import`/`export`, not `require`/`module.exports`.
- **`scripts/`**: CI/build-time Node scripts that aren't Eleventy config or template data — distinct from `src/js/`, which is browser-shipped JS passthrough-copied to the output. `scripts/lighthouse-audit.mjs` and `scripts/strava-refresh.mjs` (see the JavaScript section below for both), sharing `scripts/lib/format-json.mjs`.
- **`src/sw.js`** (the offline-support service worker) deliberately lives outside `src/js/`, passthrough-copied straight to `/sw.js` at the output root instead of `/js/sw.js` — see the JavaScript section below for why. `src/icons/` (PWA/favicon icon) and `src/manifest.webmanifest` (web app manifest) are also explicitly registered `addPassthroughCopy` entries, same pattern as `CNAME`.

## CSS

- **Plain modern CSS only** — no preprocessor (Sass/Less) and no utility framework (Tailwind, Bootstrap). This was a deliberate choice made during the site's initial design/planning session to keep the build pipeline minimal — it isn't currently backed by a standalone ADR; if that choice ever gets revisited formally, that's where it should land.
- One stylesheet, `src/css/style.css`, passthrough-copied to `/css/style.css`. Custom properties (`:root { --... }`) are the mechanism for theming/tokens, not a build-time preprocessor.
- **Visual direction**: "Data-dense dashboard" — tight spacing, badge/panel treatment for job dates and skills, system-ui sans-serif, `0.95rem` base size, `1.35` line-height. Confirmed via [wayfinder map #17](https://github.com/guntherjh/guntherjh.github.io/issues/17) and its tickets; don't redecide this without going through a similar process.
- **Light/dark theming**: two palettes switched on an `html[data-theme]` attribute — `light` and `dark` tokens defined as separate `:root`-level blocks in `style.css` (`--color-bg`, `--color-panel`, `--color-text`, `--color-muted`, `--color-accent`, `--color-border`). Both palettes are independently contrast-checked against WCAG AA, not derived by inverting one palette — retune both if either changes.

## Accessibility

- **Strive to be as accessible as possible** — this is a first-class, standing concern, not a minimum-bar checkbox. Evaluate every page, component, and content change against it as you make it, not just at the eventual visual redesign (issue #4). "It'll be accessible after the redesign" is not an acceptable deferral.
- **Semantic HTML first.** Use the element that means what you're building (`<nav>`, `<main>`, `<button>`, `<time>`, heading levels in document order) before reaching for ARIA — ARIA fills gaps semantic HTML can't cover, it doesn't replace it.
- Concretely, that means (non-exhaustive, but the recurring checks): meaningful `alt` text on images, a single logical heading hierarchy per page, visible focus states on interactive elements, sufficient color contrast, and keyboard operability for anything a mouse can do.

## JavaScript and performance

- **HTML and CSS over JavaScript.** Solve a problem with markup and styling first; reach for JavaScript only when semantic HTML/CSS genuinely can't do the job.
- **Native JS over third-party libraries.** When JavaScript actually is needed, prefer browser-native APIs before adding a dependency.
- **Third-party JavaScript always requires a discussion, and the decision must always be documented — no silent adds.** If native APIs and vanilla JS genuinely can't cover the need, discuss why before adopting the dependency. Always write down the decision and its tradeoffs; use an ADR under `docs/adr/` when the decision is hard to reverse, non-obvious, or a real tradeoff between genuine alternatives (the same bar this repo's other ADRs use), otherwise a note in the PR description — but the "always document" requirement itself has no exception, only the format varies.
- **Performance is a standing concern**, not a one-time audit — keep payload size and runtime cost in mind for every change, especially anything that adds JavaScript.
- **Be deliberate about the main thread.** Only run code on the main thread that must run there; prefer approaches that keep it free (native browser behavior, CSS, deferred/async loading) over blocking work.
- **Theme toggle** (`src/js/theme-toggle.js`): a real switch (`role="switch"`/`aria-checked`, track + sliding thumb showing ☀/☾), not an icon button — binary light/dark, defaults to `prefers-color-scheme` until the visitor explicitly overrides it, sticky `localStorage` override. The *initial* theme is applied by a deliberately inline (not external) `<script>` in `base.njk`'s `<head>`, before first paint — an external script would load after the initial render and cause a visible flash of the wrong theme. Two `.theme-toggle` buttons exist in the DOM (desktop header copy, mobile hamburger-panel copy — see Responsive design below); `theme-toggle.js` wires and syncs both via `querySelectorAll`, and is loaded without `defer` (it's the last thing in `<body>`, so nothing is blocked) to tighten the window before it corrects `aria-checked`. The switch's *visual* state is deliberately keyed off `html[data-theme]` in CSS, not off `aria-checked` — `data-theme` is already correct pre-paint, so the switch never visually flashes the wrong state regardless of script timing; only the ARIA announcement has a (small, tightened) window to catch up. Same `localStorage` pattern as `src/js/about-sections.js`.
- **Linting and formatting**: [Biome](https://biomejs.dev/) (`biome.json`), replacing ESLint + Prettier — see [ADR 0004](docs/adr/0004-biome-over-eslint-prettier.md). One tool covers both; linting is scoped to `.js` files via `biome.json`'s `overrides` (mirroring the old ESLint config's Node-vs-browser-context globals split), formatting covers JS, CSS, and JSON.
- **Indent**: tabs (Biome's default) — not the 4-space convention this repo used under Prettier.
- Biome automatically leaves `package-lock.json` alone (npm-managed, would just get rewritten — built into Biome, no config needed) and doesn't recognize Nunjucks `.njk` templates as a supported language, so they're untouched the same way Prettier never formatted them.
- `npm run lint` / `npm run format` / `npm run format:check` for local dev; `npm run check` (`biome ci .`) is the single combined command CI runs — enforced as a required check on every PR (see Git workflow below), not just a local nicety.
- **Lighthouse widget** (`scripts/lighthouse-audit.mjs`, `src/_data/lighthouse.json`, rendered in `about.njk`'s "This site" section): third-party dependency discussion, per the rule above — `lighthouse` (Google's own CLI/programmatic tool) plus its `chrome-launcher` dependency, both `devDependencies`, used only in CI, never shipped to visitors. No native/vanilla alternative exists for running a real Lighthouse audit. Settled via `/grill-with-docs`, research at `docs/research/lighthouse-widget.md`, and [ADR 0005](docs/adr/0005-post-deploy-lighthouse-audit.md); full tradeoffs (tool choice vs. `@lhci/cli`/plain-CLI-without-a-wrapper, `workflow_run` vs. same-file job chaining) recorded there rather than repeated here (guntherjh/guntherjh.github.io#41). The script audits the real production URL (not a CI-local build) via a `.github/workflows/deploy.yml` job, `needs: deploy` — runs after every merge to `master` once the site's actually deployed, waits ~90s for deploy-to-live propagation (no documented lag figure exists to time this precisely against), then lands `src/_data/lighthouse.json` (the Lighthouse Snapshot) via `.github/actions/land-data-pr` (see below) rather than a direct push. Freshness is tied to merge activity only — no separate scheduled run; since that merge is itself a push to `master`, it naturally re-triggers this same workflow, so no explicit redeploy step is needed. That re-trigger is exactly the hazard it sounds like, though: every real Lighthouse audit differs slightly from the last (network/timing variance in metrics like LCP), so left unguarded, a re-audit triggered by the job's own prior Snapshot-update merge would almost always find a new diff and commit again — an infinite merge/redeploy/re-audit loop, observed live in production before being caught and cancelled mid-run ([guntherjh/guntherjh.github.io#47](https://github.com/guntherjh/guntherjh.github.io/issues/47)). The `lighthouse` job's `if:` guards against this by skipping whenever the triggering push's own commit message is this job's own commit message ("Update Lighthouse Snapshot") — a genuine content-changing push, a Strava Snapshot push, or a manual `workflow_dispatch` still gets a fresh audit. A failed audit leaves the previous Snapshot in place and fails only this one job, not the site's actual deploy, which already succeeded before this job starts. Needs Node 22 (`lighthouse`'s own requirement) — its own `actions/setup-node` step, independent of `build`/`deploy`'s Node 20.
- **Strava widget** (`scripts/strava-refresh.mjs`, `src/_data/strava.json`, rendered in `about.njk`'s "Me" section): no new npm dependency — the script uses only Node built-ins (`fetch`, `child_process`) plus the `gh` CLI, pre-installed on GitHub-hosted runners. Settled via `/wayfinder` (map: [Strava Widget: data spec #24](https://github.com/guntherjh/guntherjh.github.io/issues/24)) after an earlier attempt at Strava's free embed feature turned out non-functional in practice (redirects anonymous visitors to Strava's login regardless of privacy settings, root cause on Strava's end undetermined — see #24's Decisions so far). `.github/workflows/strava-refresh.yml` runs **daily** (`schedule`, not merge-tied — contrast with the Lighthouse widget), fetching the last 5 Activities and per-sport recent (4-week) Stats from Strava's API, landing `src/_data/strava.json` via `.github/actions/land-data-pr` (see below) rather than a direct push. No explicit redeploy step, same as the Lighthouse widget: that merge is itself a push to `master`, which naturally re-triggers `deploy.yml`, so fresh data goes live same-day without the job forcing it. (An earlier version of this job forced a redeploy explicitly via `gh workflow run deploy.yml` on the assumption a PAT-authored merge wouldn't otherwise trigger one; that assumption predated `land-data-pr` switching to a PAT and turned out to be false — confirmed live when the Lighthouse widget's own PAT-authored merges re-triggered `deploy.yml` on their own — so the explicit step was just deploying twice per refresh and was removed.) OAuth credentials (`STRAVA_CLIENT_ID`/`STRAVA_CLIENT_SECRET`/`STRAVA_REFRESH_TOKEN`) plus a fine-grained PAT (`GH_PAT_SECRETS_WRITE`, needed because the default `GITHUB_TOKEN` can't manage Actions secrets at all) live as **environment secrets** on a dedicated `strava` environment, not repository secrets — only a job that explicitly declares `environment: strava` can read them. Strava rotates the refresh token on every use, so the script updates `STRAVA_REFRESH_TOKEN` via `gh secret set` (stdin, never a CLI argument or log line, with an explicit `::add-mask::` before the value could appear anywhere) each time it changes. `about.njk` guards rendering with `{% if strava %}` since the data file didn't exist until the first Refresh Job run (no live credentials available to seed it during implementation, unlike the Lighthouse widget's build-time-fetchable public data).
- **Landing automated data-file updates** (`.github/actions/land-data-pr`, shared by the Lighthouse and Strava widgets' refresh jobs above): `master`'s branch protection requires status checks that only run on pull requests, with no bypass for any actor — a direct `git push` to `master` can never succeed there, regardless of credential (discovered via a real failing run, not anticipated in either widget's original design — [guntherjh/guntherjh.github.io#47](https://github.com/guntherjh/guntherjh.github.io/issues/47)). This composite action instead commits to a fresh, run-unique branch, opens a PR, and enables GitHub's native auto-merge, then polls (bounded, 5 minutes) for it to actually reach `MERGED` before returning. Deliberately uses a **PAT** (`GH_PAT_PR_AUTOMATION`, a repository secret — fine-grained, scoped to this repo's Contents and Pull requests permissions), not the default `GITHUB_TOKEN`, for the `gh pr create`/`gh pr merge` calls specifically: GitHub's docs describe `GITHUB_TOKEN`-authored `pull_request` events as landing in an approval-required state, which would mean `checks.yml`'s required checks never actually run and auto-merge waits forever — a PAT-authored PR has no such gate. Repo-level "Allow auto-merge" and "Automatically delete head branches" are both enabled to support this. The throwaway branches this creates (`data/lighthouse-snapshot-<run-id>`, `data/strava-snapshot-<run-id>`) deliberately don't follow the `issue-<N>-<slug>`/`chore/<slug>` convention below — they're bot-generated and auto-deleted on merge, never meant for a human to interact with.
- **Offline support** (`src/sw.js`, `src/js/register-sw.js`, `src/manifest.webmanifest`, `src/icons/icon.svg`; [guntherjh/guntherjh.github.io#5](https://github.com/guntherjh/guntherjh.github.io/issues/5)): no new dependency — hand-written vanilla service worker, not Workbox; the site's asset list is small and static enough that a generated build manifest/precache list wasn't worth the dependency. `src/sw.js` precaches the app shell (home, about, resume, blog index, CSS, the browser JS files) on install, then uses network-first-falling-back-to-cache for every same-origin GET on top of that — prioritizing freshness for a content site where pages genuinely change, while still making any page a visitor actually loads available offline afterward, not just the precached core. `src/js/register-sw.js` registers it, deferred to the `load` event, swallowing registration failures silently (offline support is a progressive enhancement, not something that should surface an error to a visitor whose browser doesn't support it). **Cache versioning**: `CACHE_NAME` embeds a build timestamp so a new deploy always gets a fresh Cache Storage entry, and the `activate` handler purges every cache that doesn't match the current version — verified live (not just read from the code) by rebuilding mid-session and driving the browser's actual service worker update lifecycle (`registration.update()`, waiting for the new worker's `statechange` to `"activated"`) and confirming the old cache was gone afterward. The timestamp itself is injected by a post-build `eleventy.after` hook in `eleventy.config.js` that string-replaces a `__CACHE_VERSION__` placeholder in the already-copied `_site/sw.js`, rather than making `sw.js` a Nunjucks template (`.njk`) — this keeps it ordinary browser JS that Biome lints and formats like every other file in `src/js/`, rather than escaping tooling coverage the way `.njk` templates already do. `src/sw.js` itself lives outside `src/js/` (though `biome.json`'s override still covers it) because a service worker's default scope is the directory it's served from, and GitHub Pages has no way to widen that via a `Service-Worker-Allowed` header (a static host, no custom response headers) — so it has to be served from the site root, and `eleventy.config.js` remaps its passthrough copy accordingly. The icon itself is a hand-written SVG monogram (`src/icons/icon.svg`) — the site's favicon and the manifest's `sizes: "any"` entry both reference it directly. Chrome's installability check additionally requires PNGs at specific pixel sizes (192px and 512px; confirmed against Chrome's own documented criteria, not assumed — an SVG alone doesn't satisfy it even with `sizes: "any"`), so `icon-192.png`/`icon-512.png` are generated from the same SVG and committed as static assets — one-off, by hand, via a throwaway Playwright script (rendered the inlined SVG markup at a fixed viewport and screenshotted it), not a project dependency or a build step; nothing at build/CI time regenerates them, so if the source SVG ever changes, they need regenerating too. `icon-192.png` is also linked as `apple-touch-icon`, since iOS's "Add to Home Screen" doesn't read the manifest's `icons` at all. Verified live via Chrome DevTools Protocol's `Page.getInstallabilityErrors` (the same signal Chrome's own install-prompt UI uses) returning zero errors, not inferred from the criteria alone.

## Responsive design

- **The site should work well at every screen size**, from small phones through wide desktops — this applies to every page and component, not just a subset.
- Prefer fluid, relative-unit layouts (`%`, `rem`, `clamp()`, flexbox/grid) over fixed pixel widths that only look right at one size.
- When adding or changing layout, check it at a narrow mobile width and a wide desktop width at minimum, not just whatever window size you happen to be developing in — this is genuinely required, not a formality: the initial issue #20 implementation shipped without it and needed a real follow-up round (the mobile nav below) once actually checked.
- **Mobile nav** (below `640px`, `.nav-toggle` in `base.njk`): nav links + theme toggle collapse behind a hamburger button (native `<details>`/`<summary>` — same mechanism as the About page's collapsible sections), revealed in a `position: absolute` overlay panel so opening it doesn't grow the header's height. **Desktop (`.site-header-controls`) and mobile (`.nav-toggle`) controls are two independent, duplicated markup blocks** in `base.njk`, not one nav/toggle shown twice via a single-markup trick — an earlier attempt relied on CSS overriding `<details>`'s native closed-content hiding to keep content visible above the breakpoint, which wasn't reliably overridable that way and made the desktop controls disappear entirely. Keep both copies in sync by hand (marked with warning comments in `base.njk`) when nav links or the toggle change.
- **Mobile nav, closing on outside click** (`src/js/nav-toggle.js`): the base open/close toggle above is genuinely zero-JS (native `<details>` behavior alone), but closing it on an outside click/tap is not something `<details>` provides, and there's no pure-CSS way to detect a click outside an element — so this one behavior needs a small script. Listens for `pointerdown`, not `click`: confirmed via testing against WebKit (Safari's engine) with touch emulation that tapping a plain, non-interactive element fires `touchstart`/`touchend` but never a `click` event at all — WebKit only synthesizes `click` from a touch tap on elements it treats as interactive. A `click`-based listener would silently never fire for most outside taps on Safari/iOS. `pointerdown` fires for every tap regardless of target, confirmed on both Chromium and WebKit, and fires early enough (before `<details>`'s native toggle, which is tied to `<summary>`'s later `click` activation behavior) that it doesn't race the tap that opens the menu.

## Git workflow

- **One branch per ticket.** Branch off `master` (never commit ticket work directly to `master`). Branch names: `issue-<N>-<short-slug>` for ticket work, `chore/<slug>` for non-ticket housekeeping.
- **One PR per ticket**, opened against `master`, referencing the resolved issue in the PR body.
- **Commit messages**: imperative subject line; a body explaining *why* when it's non-obvious, not just what changed. **From issue #8 onward**: for commits that resolve a tracked issue, put the issue's full URL on its own line at the end (e.g. `https://github.com/guntherjh/guntherjh.github.io/issues/2`) instead of a bare `Closes #N` shorthand, and omit the `Co-Authored-By` trailer. Earlier commits in this repo's history predate that convention and still use `Closes #N` plus a `Co-Authored-By` trailer — don't take them as the current standard.
- **Verify before committing**: run `npx eleventy` and confirm it builds clean; for content changes, spot-check the rendered `_site/` output before committing. Also run `npm run check` if the change touches `.js`, `.css`, or `.json` files.
- Once a ticket's work is committed, run `/code-review` against `master` before opening the PR.
- **Required checks**: every PR against `master` runs two checks — check (Biome), build (`.github/workflows/checks.yml`) — and branch protection on `master` requires both to pass (plus admins, `enforce_admins`) before a PR can merge. Two jobs, not three, since [ADR 0004](docs/adr/0004-biome-over-eslint-prettier.md) collapsed the former separate lint/format-check jobs into one combined `biome ci` job. These automate what the two bullets above ask you to do manually; CI is the backstop, not a substitute for checking locally first.
